## Product design

### Goals / Non-goals

**Goals**: add tools that close the three capability gaps identified above — admin settings, policies, and investigations — using the same per-request-credential, read-only, one-tool-per-upstream-endpoint pattern the existing 14 tools already use.

**Non-goals**:
- No write/mutate tool (API key create/update/delete/refresh, policy edit). The ticket says "Review", which is read-only, and matches the repo's existing stance: "All tools are read-only; there are no write or delete tools" (`src/cisco_umbrella_mcp/server.py:123`).
- Not resolving "Policies" beyond Destination Lists / Application Lists. Cisco's Policies v2 API, as far as this design pass can confirm against public docs, does not expose a single "list security-policy objects" endpoint — see Open Question OQ1.
- No change to credential handling, transport, or the behavior of the existing 14 tools.

### Acceptance criteria AC1..AC7

- **AC1**: Given a valid Umbrella API key/secret pair, When a caller invokes a new admin tool, Then it gets back the account's Umbrella API key list (id, label, scopes, status) and never a key secret.
- **AC2**: Given a resolved `organization_id`, When a caller invokes a new policies tool for destination lists, Then it gets back that customer's destination lists (or, given a `destination_list_id`, the destinations inside one list).
- **AC3**: Given a resolved `organization_id`, When a caller invokes the application-lists tools, Then it gets back that customer's application lists and application usage counts.
- **AC4**: Given any domain name, When a caller invokes the new domain-categorization tool, Then it gets back Cisco's security/content categorization for that domain, with no `organization_id` required (Investigate is a global lookup, not per-customer).
- **AC5**: Given any domain name, When a caller invokes the risk-score and WHOIS tools, Then it gets back Cisco's numeric risk score and the domain's current WHOIS record respectively.
- **AC6**: Given a gateway-mode request missing the `X-Umbrella-Api-Key`/`X-Umbrella-Key-Secret` headers, When any of the 8 new tools is called, Then it returns the same `not_configured` structured error the existing 14 tools return — no new header names are introduced.
- **AC7**: Given an upstream 401/403/404/429/5xx response from any new endpoint, When the corresponding tool calls it, Then it returns the same structured error envelope with the same status-to-code mapping the existing tools use — no stack traces, no raw HTML.

### Open questions

- **[not blocking] OQ1** — Cisco's Policies v2 documentation reachable in this session confirms GET endpoints for Destination Lists and Application Lists, but no single "list/get security-policy objects" endpoint. Default: treat destination lists + application lists as the "policies" deliverable — in the Umbrella console these *are* what an admin configures as policy. If implementation finds an actual policy-object endpoint against the live OpenAPI spec (same verification habit the README's Known Gaps section already follows for the other 10 endpoints), add it as a bonus tool; otherwise AC2/AC3 satisfy this requirement as scoped.
- **[assumed] OQ2** — Assumed the Investigate API is reachable at `https://api.umbrella.com/investigate/v2/...` under the same OAuth2 client_credentials flow and the same API key/secret pair (Cisco's docs note the legacy `investigate.api.umbrella.com` host "was moved to the legacy Umbrella API", implying consolidation into `api.umbrella.com`). If the key's granted scopes don't include `investigate`, calls will 403 — a vendor-console entitlement issue, not a code bug, to be logged the same way the existing Known Gaps section logs the App Discovery 403. If Cisco actually requires the separate legacy host with a different static-token auth, the Change List's `investigate.py` becomes a 2-line change (new base host, same per-request header credentials) — no architecture change. Not blocking.
- **[not blocking] OQ3** — Whether Investigate lookups should be `organization_id`-scoped like the reporting tools. Assumed no: domain reputation is a global Cisco dataset, not per-managed-customer data, matching how `list_customers`/`get_providers_console` already skip `organization_id`.

## Tech design

### Conclusion

Add three new read-only tool modules (`admin.py`, `policies.py`, `investigate.py`) to the existing FastMCP server, each following the exact structure of `tools/reports.py` — one `@mcp.tool` per upstream GET endpoint, same `UmbrellaClient.get()` call, same error envelope. No change to `api_client.py`, `config.py`, or the credential/auth model: all three new groups reuse the same two gateway headers already required today. The only new surface is 8 new tool functions plus their registration in `server.py`.

### Where the current implementation lives

- `src/cisco_umbrella_mcp/server.py:159-164` — tool-module registration point (`from .tools import reports; reports.register(mcp, client_factory)`).
- `src/cisco_umbrella_mcp/tools/reports.py:1-16` — the pattern every new tool module copies: module docstring stating the naming convention, a `register(mcp, client_factory)` entry point, `@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))`.
- `src/cisco_umbrella_mcp/tools/reports.py:33-92` — concrete worked example (`cisco_umbrella_get_activity_dns`): parameter docs via `Annotated[..., Field(...)]`, `client_factory()` + `NO_TOKEN` check, `client.get(path, params=..., organization_id=...)`, `dump_json_capped(result)` / `UmbrellaError.to_envelope()`.
- `src/cisco_umbrella_mcp/api_client.py:124-198` — `UmbrellaClient.get()`, the sole HTTP entry point; reused unchanged by all 8 new tools.
- `src/cisco_umbrella_mcp/tools/_common.py:1-8` — `NO_TOKEN` shared error constant, reused unchanged.
- `README.md:185-231` — the tool table and Known Gaps section that must be updated (8 new rows; "Policies/Investigate/Key Admin" removed from the explicitly-out-of-scope sentence once they land).

### Option analysis

No table needed — "no alternative": this repo has exactly one established pattern for a read-only reporting-style tool (one `@mcp.tool` wrapping one GET endpoint via `UmbrellaClient.get()`), used uniformly by all 14 existing tools. A single mega-tool with a `resource` enum parameter, or a generic passthrough tool, would break the "tool name tells the agent what it does" design stated in `server.py`'s `instructions=` string, and would defeat the gateway's per-tool allowlist (`README.md:60-62`, "Controlled: per-role, per-tool allowlist, deny by default"). Following the repo's existing architecture, not introducing a second shape, is the only option considered.

### Data & API contract

All 8 tools are read-only GETs through the existing `UmbrellaClient.get(path, params, organization_id)`. Response shapes below are from Cisco's public API reference; exact field names should be confirmed against a live call during implementation and any surprise documented in README Known Gaps, the same way the existing 10 endpoints already are.

| Tool | Upstream call | `organization_id` | Response shape (example) |
|---|---|---|---|
| `cisco_umbrella_list_api_keys` | `GET /admin/v2/apiKeys` | No (provider-level) | `[{id, label, scope: [...], createdAt, lastUsedAt, status}]` — never a secret field |
| `cisco_umbrella_list_destination_lists` | `GET /policies/v2/destinationlists` | Required | `[{id, name, access: "allow"\|"block", isGlobal, destinationCount}]` |
| `cisco_umbrella_get_destination_list_destinations` | `GET /policies/v2/destinationlists/{id}/destinations` | Required | `[{id, destination, type, comment}]` |
| `cisco_umbrella_list_application_lists` | `GET /policies/v2/applicationLists` | Required | `[{id, name, isDefault, applicationCount}]` |
| `cisco_umbrella_get_application_usage` | `GET /policies/v2/applications/usage` | Required | `[{applicationId, name, category, usageCount}]` |
| `cisco_umbrella_get_domain_categorization` | `GET /investigate/v2/domains/categorization/{domain}` | No (global) | `{"<domain>": {status: -1\|0\|1, content_categories: [...], security_categories: [...]}}` |
| `cisco_umbrella_get_domain_risk_score` | `GET /investigate/v2/domains/risk-score/{domain}` | No (global) | `{risk_score: 0-100, ...feature breakdown}` |
| `cisco_umbrella_get_domain_whois` | `GET /investigate/v2/whois/{domain}` | No (global) | `{domain, registrant, registrar, created, updated, expires, nameServers: [...]}` |

**Errors**: identical envelope to the existing tools — `_STATUS_TO_CODE` in `api_client.py:33-41` already covers 400/401/403/404/422/429 and 5xx; no new status codes are expected from these endpoints, so no change to that mapping.

**Backward compatibility**: purely additive. 8 new tools, zero changes to the 14 existing tool signatures, zero changes to the two credential headers or the auth flow. Nothing that calls the server today can break.

**DB**: none — this is a stateless MCP wrapper with no database.

### Key flow / sequence

Identical to every existing tool (pure reuse): Gateway → `GatewayTokenMiddleware` reads the two headers into a contextvar → tool handler calls `client_factory()` → `UmbrellaClient(api_key, key_secret)` → `_login(organization_id)` mints a (child-)scoped bearer token → `GET <path>` → JSON or `UmbrellaError` → `dump_json_capped` / `error_envelope` → MCP response. No new step is introduced; see `api_client.py:143-198` and `server.py:27-40` for the sequence this unit reuses verbatim.

### Non-functional

- **Idempotency/concurrency**: all 8 new tools are GET-only (no state mutation), so repeated or parallel calls are naturally idempotent — the same guarantee the existing 14 tools already have via the stateless, re-authenticate-every-call design (`api_client.py:124-137` docstring).
- **Performance**: same per-call token-mint cost (~1 extra round trip) as every existing tool; no caching introduced, deliberately — caching across tenants would risk leaking scope.
- **Security**: no new credential surface — same two headers as the other 14 tools. `cisco_umbrella_list_api_keys` must never surface a key secret; Umbrella's own API doesn't return one after creation, so this is enforced by the vendor, and the response should be passed through unmodified.
- **Multi-tenant isolation**: identical to the existing 14 tools — policies/admin tools that take `organization_id` are scoped via `X-Umbrella-OrgId` at token-mint time (`api_client.py:143-168`), never cached, so no cross-tenant leakage (see AC2/TC4). Investigate tools are intentionally *not* `organization_id`-scoped because Cisco's threat-intel dataset is global, not per-customer — same reasoning already documented for `list_customers`/`get_providers_console`.
- **Observability**: no new logging needed beyond what `UmbrellaError`/`_raise_for_status` already provide (upstream status + message). Any unexpected response shape found during live verification gets documented in README Known Gaps, same as today.

### Rollout & rollback

Single-repo, additive change: merge to `main`, published once via the review leg's `mcppub publish` (not part of this design/dev unit). Rollback is a plain `git revert` of the merge commit — no data migration, no credential change, so revert is safe at any time. No feature flag is needed: new tools are simply absent from `tools/list` until the gateway's per-tool allowlist enables them, matching the existing "deny by default" model (`README.md:60-62`).

### Risks & dependencies

- **Entitlement risk**: as with App Discovery today, the `investigate` scope and the `admin.apikeys:read` scope may not be granted on MSPbots' current Umbrella API key — a 403 here is a vendor-console permission issue, not a code bug, exactly like the App Discovery 403 already documented in Known Gaps. Mitigation: document it the same way, don't treat it as blocking.
- **Spec-confirmation risk**: OQ1/OQ2 — the exact Policies "policy object" endpoint and the Investigate host/scope need confirming against Cisco's live OpenAPI spec at implementation time (the same "pulled the raw spec, not summarized" practice the README already describes for the other 10 endpoints). Non-blocking — the fallback (destination/application lists as the "policies" deliverable; consolidated `investigate/v2` host) is a reasonable default if the spec doesn't pan out differently.
- No dependency on another ticket or another repo; no gateway/control-plane change — this stays entirely inside `cisco-umbrella-mcp`.
